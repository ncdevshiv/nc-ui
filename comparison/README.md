# NC-UI against Electron and Tauri

This directory is a measured comparison: two real applications, one written for Electron and one
for Tauri, each cloned from its upstream repository, each ported to NC-UI, and each side measured
on the same workload. The claim it tests is the one the project makes — that an NC-UI application
is smaller, starts faster, uses less memory and answers its page faster than the same application
on either incumbent.

The comparison is a harness, not a table transcribed into a document. Every number is produced by
`bench/compare.py`, which builds the applications, launches them, and writes a machine-readable
report to `bench/results/windows.json`. The harness is the evidence; the table below is a reading
of it.

## The applications

| App | Framework | Upstream | Commit | NC-UI port |
| --- | --- | --- | --- | --- |
| `electron-quick-start` | Electron 45 | `electron/electron-quick-start` | `ecfb901f` | `ports/electron-quick-start` |
| `example-tauri-app` | Tauri 1.2 | `AlexMercedCoder/example-tauri-app` | `c178b4f8` | `ports/tauri-word-signal` |

Both are the real upstream sources, cloned by the harness into `comparison/.originals/` (git-ignored,
pinned by commit in `manifest.json`). The harness copies the benchmark instrumentation from
`bench/instrumentation/` over the clone before building, so the upstream sources are never edited
and the changes are reviewable in one place.

The Electron application is the official quick start: a window, a page, and a preload that fills
the runtime's version labels. The Tauri application is a standalone SolidJS app: a page with a
button that invokes a Rust command and displays the answer, plus a menu that maximises and
minimises the window.

## The ports

A port preserves what the application *does*, not the framework it was written for.

- `ports/electron-quick-start` — the same window and page. Instead of Electron's version labels,
  the page asks the runtime through the bridge and shows the runtime version, API version,
  platform and method count. The bridge call is the same shape as the original's preload call:
  the page asks a native side what it is.
- `ports/tauri-word-signal` — the same page, button and result. The native command is a NC-UI
  component (`plugins/word_signal.wat`) that the page did not write, loaded under
  `run.components` and invoked through the component host. The component is generated by
  `tools/make_word_signal_component.py`; the generator and the artifact agree, and `--check`
  fails if they drift.

The Tauri application's menu is the one behaviour the port does not reproduce, and the reason is
a project policy rather than an oversight: a native menu bar on Windows needs `muda`'s
`init_for_hwnd`, which is `pub unsafe fn`, and `unsafe_code = "forbid"` is workspace-wide. The
actions the menu performed (maximise and minimise) are available to a page through
`window_state`; the menu bar itself is recorded as absent in `docs/known-gaps.md`. The port does
not fake it.

## How the measurement works

`bench/compare.py` runs each configuration — the original on its framework and the port on
NC-UI — five times by default and reports the minimum, median, p90 and maximum. The idle
measurements come from a separate launch that carries no benchmark trigger, so the
benchmark's own allocations are not charged to the framework; the IPC measurement comes from
the launch that does carry it. It measures:

- **Cold start** — the time from the process being created to a visible window whose title is the
  application's own. The window is found with `EnumWindows`/`GetWindowTextW`, so the measurement
  is of a window the platform actually drew, not of a process that merely exists.
- **Idle working set** — two seconds after the window appears, the summed working set of the
  process and every descendant. The descendant walk uses a Toolhelp snapshot, so Electron's
  renderer and GPU processes and the WebView2 processes Tauri and NC-UI spawn are all counted.
- **Idle CPU** — the framework process's CPU time over a two-second window, as a percentage
  of one core, read with `GetProcessTimes`. A runtime that wakes itself on a timer when
  nothing is happening pays for it here. The webview's own processes are not counted: their
  background work belongs to the page, not to the runtime.
- **IPC round trip** — the page performs 200 correlated request/response calls through its own
  framework's bridge and writes the elapsed time to a file. For Electron this is `ipcRenderer`
  against an `ipcMain` handler; for Tauri it is `invoke` against the app's `return_string`
  command; for NC-UI it is `window.ncui.invoke` against the runtime's `list_windows` command.
  `comparison/manifest.json` names the command each original is measured against, and the
  harness asserts the instrumentation still handles it before building — a rename on either
  side fails the run rather than quietly measuring a different bridge. Each side measures its
  own bridge, which is the thing being compared. The command's own cost is small beside the
  round trip: the NC-UI figure is the same with a heavier command, so the gap is the seam, not
  the handler.
- **Distributed size** — the bytes a user would install: the Electron distribution plus the
  application's own files, the Tauri binary plus its built frontend, or the NC-UI runtime plus
  the port directory. The NC-UI runtime is rebuilt by the harness with `ncui-cli/wry-host` on
  every run, so the figure is always the renderer-carrying build rather than whatever
  `target/release/ncui.exe` happened to contain.

## Running it

```sh
python comparison/bench/compare.py
```

The harness clones the applications, installs their dependencies, builds them, applies the
instrumentation, runs every configuration and writes `bench/results/windows.json`. It needs
Node.js, npm, Rust and MSVC on Windows; the window poll and the memory walk are Win32 entry
points through `ctypes`, so the harness is Windows-only.

## Results

The current report is `bench/results/windows.json`, produced by five repeats of every
configuration on Windows x86_64. The table reads the median (p50); the report carries the
minimum, p50, p90 and maximum for every timing. The timing figures move between runs on a
shared machine — the report records each IPC repeat's own spread — so the committed report is
one run and the relative ordering is the finding, not the third decimal. `--repeats` raises the
count and `--rounds` raises the IPC workload.

Three independent runs of five repeats each have been compared. The ordering on cold start,
idle working set and distributed size was identical every time. The idle CPU row moved: it
read 0.78 % for NC-UI until the asset server's accept poll was removed, and 0.00 % after —
a change large enough to see because it is not a timing that drifts, it is a wakeup rate that
was either there or not. A reader comparing the three frameworks should read the ordering and
the rough ratios rather than a single run's third decimal.

### What the numbers say, honestly

NC-UI is not superior on every metric, and this section does not claim it is. It is
dramatically smaller and starts dramatically faster than Electron, it is level with Tauri on
startup, and all three measure 0.00 % CPU at idle. It is slower than both on IPC, larger than
both at idle, and larger than Tauri on disk. The reasons are architectural rather than
accidental:

- **The release build carries the GPU island renderer.** `wry-host` enables `gpu-islands`,
  because the counter example's canvas is the feature and the documented `ncui run` command
  must serve it rather than show a blank rectangle. That is why the distributed size is
  11.3 MiB. The renderer's cost is measured rather than assumed: the same build with the window
  host but without `gpu-islands` measures 4.88 MiB, so the renderer is 6.4 MiB, and a build with
  no window host at all measures 1.64 MiB and refuses to open a window. Both were built and
  measured on this machine on 2026-11-08, and the difference is recorded here rather than hidden.

- **IPC.** A NC-UI page call crosses the webview boundary twice (the page's `postMessage`, the
  host's `evaluate_script`) and the host's event loop runs on its own thread, so the response
  makes a thread hop Electron's direct C++ IPC does not. The handler is not the cost: the
  latency suite measures one page command's in-process dispatch — capability check, handler,
  response serialisation — at a p99 of **900 ns**, against a 375 µs round trip. The other
  99.8 % is the boundary. The measured 0.375 ms is what that costs, and it has moved twice: a
  blocking wait on the engine's message channel took it from 16.4 ms to 0.52 ms, and removing
  the asset server's 2 ms accept poll — which was waking the process five hundred times a
  second and competing with every round trip — took it to 0.375 ms. Tauri's 0.281 ms is the
  same WebView2 boundary with a slightly shorter path. The reply can only be delivered by
  evaluating a script in the page, because `wry`'s public API exposes no `PostWebMessageAsJson`
  seam and `unsafe_code = "forbid"` rules out calling the COM interface directly.
- **Memory.** The runtime process is not where the difference is, and the decomposition is
  measured rather than assumed: `ncui.exe` is about **26 MiB** against Electron's **95 MiB**
  main process — 3.7× smaller — and the WebView2 renderer (53 MiB) and GPU process (68 MiB)
  are both smaller than Electron's (65 MiB and 94 MiB). The tree is larger because the
  WebView2 runtime keeps a browser process of its own at about **129 MiB**, a process
  Electron folds into its main process, plus two utility processes (62 MiB against
  Electron's one at 49 MiB) and a crashpad handler (12 MiB). The two pages are not the same
  code — a port preserves what the application does, not its framework — so the renderer row
  is not a clean framework comparison. What is clean: the runtime's own footprint is
  smaller, and the extra memory belongs to the webview runtime both frameworks host.
- **Idle CPU.** Level, and it was not always: an idle NC-UI application measured 0.78 % of a
  core against 0.00 % for both incumbents. The cause was not the page loop but the asset
  server, which accepted on a non-blocking listener and slept 2 ms between attempts — about
  five hundred wakeups a second for an application serving nothing. The wait is now a channel
  receive that `stop` wakes at once, with a 250 ms timeout kept only as the net that
  guarantees termination, and the same measurement reads 0.00 %. One caveat belongs with the
  figure: the two-second window's resolution is one Windows clock tick, 0.78 %, so a single
  tick shows up in the p90 of some repeats for Electron as well as for NC-UI. That is the
  measurement's floor, not work either framework is doing.
- **Size.** The NC-UI runtime carries the scheduler, metrics, audit log, worker pool,
  capability machinery and the GPU island renderer that a Tauri binary does not; 11.3 MiB is
  what that costs, and the renderer alone is 6.4 MiB of it (a build with the window host but
  without the renderer measures 4.88 MiB). It is 32× smaller than the Electron distribution,
  which is the comparison that matters for shipping.

The harness records what it measures. The committed `windows.json` is the artifact, and the
table above is a reading of it; if they disagree, the JSON is right.
