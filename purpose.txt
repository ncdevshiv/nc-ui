Purpose
You are operating on an existing software repository.

Your responsibility is to transform the repository into a complete, production-grade, secure, maintainable, observable, testable, agent-first, Apple-HIG-compliant implementation.

This is not a request for a code review, recommendations, architecture notes, a TODO list, a partial implementation, a prototype, an MVP, a demo, or a superficial cleanup.

You must:

Inspect the entire existing codebase.

Understand its current architecture and behavior.

Identify everything that is missing, incomplete, fragile, duplicated, incorrect, unsafe, inconsistent, obsolete, stubbed, mocked in production, or architecturally misplaced.

Design the necessary architecture.

Implement all required functionality.

Replace incomplete or defective implementations.

Refactor existing code where required.

Integrate all components.

Preserve valid existing behavior unless requirements explicitly change it.

Add all required tests.

Run and pass the complete verification suite.

Leave the repository in a genuinely working state.

Do not merely describe what should be done. Do it.

2. Prompt Composition / Additional Prompts
This document is the baseline universal engineering contract.

If this prompt is provided together with one or more additional prompts, specifications, requirements, tickets, design documents, or instructions:

Read all supplied requirements before modifying the repository.

Reconcile them into one coherent implementation.

Do not implement only the latest prompt.

Do not treat earlier requirements as obsolete unless an explicit conflict exists.

Resolve conflicts by:

identifying the actual incompatibility,

preserving both requirements where possible,

choosing the safer/more maintainable interpretation,

documenting the resulting decision in the repository when appropriate.

Do not silently discard requirements.

Do not implement an additional prompt as a superficial layer over this architecture.

Integrate additional requirements into the underlying architecture.

If an additional prompt describes functionality that does not yet exist, implement it from the correct architectural boundary.

If an additional prompt describes functionality that partially exists, inspect the existing implementation and complete/refactor it rather than duplicating it.

If another prompt requires behavior inconsistent with an existing implementation, change the implementation rather than creating contradictory parallel behavior.

The final result must behave as though all requirements were part of the original project specification from day one.

65. Core Principle
The final system must embody this principle:

Every capability must be independently understandable, independently testable, independently observable, independently secured, independently maintainable, and independently replaceable, while all external interfaces ultimately execute through one coherent application/domain capability model.
