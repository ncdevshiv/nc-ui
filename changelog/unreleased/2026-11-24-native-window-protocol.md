- **The runtime speaks the native window protocol.** `ncui.window.create` accepts a `content` parameter — `{"kind": "page"}` still the default — so `{"kind": "native", "provider": "...", "props": {...}}` opens a native window through the same parsing and validation path as a page, with the contract's rules enforced before any host is asked: no URL on a native window, a bounded provider identifier, and props of at most 64 KiB. Two methods join the agent surface behind the `window` capability: `ncui.window.native.events` polls one view event in the contract's own serialization (or null when the queue is honestly empty), and `ncui.window.native.command` delivers `update_props`/`invoke` commands, refusing out-of-bounds commands before they are sent and carrying the view's stable `native_*` refusal codes into the wire error. Both are refused with a structured `conflict` on a page window, and both are covered end to end by integration tests driven through the real dispatch pipeline. The embedding side is host-neutral: `Runtime::with_host_factory` and `Application::launch_with_factory` install any `HostFactory` the caller chooses — including a `RoutingFactory` that serves pages and native views side by side — while `with_host` and `launch_with` behave exactly as before, and the `gpui-host` feature wires the optional `ncui-gpui` dependency without the runtime naming the engine anywhere outside the feature gate.
